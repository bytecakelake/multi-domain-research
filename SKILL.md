# Multi-domain research lab (Forge · Lab · Crew · Retro)

Describe the research domain and direction as **traits**. Matching workflows are then **composed from the block catalog and saved to the library**, executed in subagent waves on top of the local data infrastructure (SQLite ledger + Parquet + DuckDB), and the results are fed back into the library. All child output is received only as files, and the parent loads it into the ledger only after machine-verifying citations, SQL, and receipts. The engine is `scripts/rlab.py` (CLI), referred to as `$RLAB`.

## When to Use

- Deep investigation across multiple sources (technology, markets, policy, scholarship, historical verification of people, events, etc.) where sentence-level evidence tracing is required.
- When you need a **new workflow tailored to the domain and direction** rather than a fixed procedure (even an unfamiliar domain can be described with traits).
- When parallel subagent collection, extraction, and refutation and quantitative analysis (SQL) must be handled together in a single ledger.
- **Do not use for:** single lookups or summaries, reading one file, format conversion of already-established facts, or code implementation and debugging (use direct tools).

## Prerequisites

- In the sandbox, the skill folder appears as the read-only `/hermes-home/skills/research/multi-domain-research` (different from the host path shown by `skill_view`). Outputs accumulate not in the skill folder but in the **lab home** (`$RLAB_HOME`, default `/workspace/research-lab`).
- The `write_file`/`read_file`/`patch` tools resolve paths against the Hermes host workspace (`workspace.*`). With the docker backend, writing to a lab-home path such as `/workspace/research-lab/...` triggers an "OUTSIDE the active workspace" warning. When this warning appears for **new file creation** (intake/traits/questions, etc.), the file may land in a different directory on the host side where `rlab` cannot find it, so write it directly inside docker with `terminal` using `cat > ... << 'EOF'` (heredoc). **`patch` on an existing file** (e.g., adding a §8 pointer to brief.md) has sometimes been applied correctly to the docker-side file even when the same warning appears (probably because find-and-replace works on file contents) — still, do not trust the warning, and after every `write_file`/`patch` to a lab-home file, confirm with `cat` in `terminal` that it was actually applied.
- Requires a Python with duckdb installed (default on this box: `/workspace/.envs/tools/bin/python`). If it is missing, `doctor` prints the install command. Forge, the ledger, and gates work with the standard-library SQLite alone; only `lake`, `sql`, datasets, and SQL evidence require duckdb.
- The **currently active option list** for `delegate_task` (check on every run that the names in the routing table are still valid). The cap on concurrently running children is a user setting (currently 4).

## Quick Reference

```bash
$RLAB forge --traits t.json --name <slug> [--fork WF] [--add B] [--drop B] [--set k=v|block.k=v]   # compose + save
$RLAB wf list | wf show <id> | wf match --traits t.json                                          # library
$RLAB init --workflow <id> --run-id R [--brief b.md --questions q.jsonl]                          # create a run
$RLAB questions --run R --file q.jsonl                                                           # load the question tree
$RLAB next --run R --dispatch --available "A,B,..."        # advance the engine + delegate_task payload
$RLAB load --run R --task T --file <staging/out/T.jsonl>  # verify + load (transaction)   [for children: begin / check]
$RLAB gate --run R [name] | status | report | waive --gate G --reason ".." | reopen --block B
$RLAB sql --run R --recipe coverage | "SELECT ..." [--hash]     # DuckDB read-only SQL, recipes: `$RLAB recipes`
$RLAB source add|set|drop ... | retry --task T [--cause env|contract|model] | dispatched --payload F | unready --payload F | refresh-inputs --block B | resume --reason R | resolve --id X0001 --status resolved|disclosed (for many: resolve --file F.jsonl)
$RLAB done --run R --block B        # mark PARENT ACTIONS (blocks the parent performed directly, e.g., access-broker) as complete to unlock the next blocks
$RLAB retro --run R [--score 0-5] --lesson "..."        # feed fitness, lessons, and mutation proposals back into the library
```

## Procedure

Full journey: **P0 Setup → P1 Traits → P2 Forge → P3 Start Run → P4 Drive Loop → P5 Analysis & Refutation Verdicts → P6 Deliverable → P7 Retro**. At the start and end of each phase, tell the user the current phase and the next one.

**P0 Setup.** Run `setup`/`doctor`. Done when: `RESULT OK`.

**P1 Traits (describing domain and direction).** First restate the request in one line to fix the interpretation. For domains where terms look alike but mean different things, such as finance or law (e.g., overseas *KRW-denominated payment* [DCC] vs *foreign-currency payment* [exchange fee]), a user correction after you have already forged a workflow throws off its domain/direction/brief/questions, so if a term is ambiguous, confirm the interpretation in one sentence before forging. If you receive a correction before a run has been created, delete the wrongly saved workflow files (`workflows/<id>.json|md`) and `forge` again with the corrected traits; even if only a label changed, rewrite the brief and questions. Write the traits JSON using the decision questions in `references/trait-rubric.md` (see `assets/traits.example.json`). Leave a one-line rationale for each value, and when uncertain, judge toward the costlier side (raise stakes and noise). Done when: every trait has an allowed value and the mode (direction) is settled on a single value.

**P2 Forge.** First look for a similar saved workflow with `wf match` (if the distance is ≤0.25, mutate it with `--fork`; otherwise compose a new one). Read the blocks, lanes, budget estimate, dropped-block reasons, and library lessons in the `forge` output, and if anything is excessive or missing relative to the questions, adjust it with `--add/--drop/--set` (block definitions and extension are in `references/blocks-and-forge.md`). Before saving, preview with `forge --no-save`, and present the user with a summary of the composition and the options (as is / lightened (e.g., double coding → single) / edit directly), each with its cost and what you would lose. If the user chooses "explain," spell out each block's role (design, collection, gating, extraction, analysis, verification, wrap-up), the dropped blocks and reasons, and the trade-offs of each option, state your recommendation, and then ask for approval again. Done when: the workflow is saved as `lab home/workflows/<id>.json|md` and the user approves the composition (blocks and expected number of tasks). If traits (access, volume, etc.) or scope change substantially, create a new workflow with `--fork` and move to a new run (for fork pitfalls and how to hand over to a new session, see "fork operations" in `references/blocks-and-forge.md`). If the user has explicitly requested an uninterrupted run to completion, record the composition, dropped blocks, and budget trimming and proceed, but confirm separately any change that raises risk (such as trimming high-risk blocks).

**P3 Start Run.** Fill in `templates/brief.md` (if `{{` remains, intake is incomplete), `init`, and write `questions.jsonl`: at most 7 top-level questions, each with a `kind` (yesno|compare|measure|trend|rank|describe|explain|forecast) and decidable `labels` (codebook), and for interpretive questions also `label_defs` (derive labels for personality and person questions from theory, and finalize drafts only after review by subagents from different model families and trial coding on public cases: see "Codebook authoring and review procedure" (`코드북 작성·검토 절차`) in `references/personality-frameworks.md`). Done when: intake and qtree are complete in `status`.

**P4 Drive loop (`next` guides P4 through P7 in order).** When a gate blocks, read the cause before resorting to a waiver (waive). If claim strength is the problem, use `rlab downgrade`; if a contradiction remains, read the source text and disclose it with a reason using `rlab resolve --status disclosed`. When collection, extraction, analysis, and refutation are finished, `next` surfaces `synthesize` as a PARENT ACTION (→ do P5 and P6), then surfaces `retro` (→ P7). `ALL DONE` appears only after P6 and P7 are finished. Repeat until everything is done.
1. `next --dispatch --available "<current option list>"` — the engine marks ready tasks as `ready` (emitted, delegation unconfirmed) and prints the `delegate_task tasks` JSON (`goal` and `context` are fixed ASCII pointers; the full contract exists in files).
2. Pass that JSON as-is to `delegate_task(tasks=[...])` (at most 4 concurrent; the same option is limited by `max_per_option`, default 3). After delegating, confirm with `rlab dispatched --payload dispatch_NNN.json` (a child's `begin` also confirms automatically). If you decide not to delegate, revert with `rlab unready --payload ...` (use `retry` only for attempts that were delegated and failed). If `option` is empty (`none of [...] is available`), choose from the currently active options using the tiers in `references/crew-contracts.md` and add `option` directly to each task. If you pass the same `--available` list to every `next`, `option` is filled in automatically for roles that have candidates. After dispatching, end your response and wait for the completion notification (no polling); when it arrives, proceed with `load` for each task → `next --dispatch`. Duplicate candidates across lanes are filtered out by `load` as dup, which is normal.
   - **Pass the JSON printed by `next` as the payload, unchanged (do not rewrite `goal` or `context` by hand):** both are fixed ASCII sentences containing only the task id, block, role, and absolute paths, so the `"없음"` ("none") and empty-string placeholders and mojibake that arose from hand-copying no longer occur (the full task purpose exists in the contract file), and if `addendum.md` exists, its path and the precedence rule are automatically appended to `context`. If the run id or `RLAB_HOME` is not ASCII, `next` warns on stderr. When putting Korean or other non-ASCII text into other tool parameters, do not hand-compute `\uXXXX` escapes; write the plain UTF-8 string directly into the parameter — even without typos, silent mojibake (`입력`→`입륥`) can occur.
   - **Handling workflow-critic findings:** after `load`, read the findings yourself, decide for each block/warn/info finding whether to accept, reject, or disclose it as a limitation, and record this in `reports/critic_dispositions.md`. Design reinforcements are written not by editing workflow.json but in `addendum.md` in the run directory (collection boundaries, source roles, definition of independence, per-question coding rules, parent follow-up actions). For every payload emitted afterward, `addendum.md` automatically gets its absolute path and the rule "on conflict, the addendum's prohibitions and restrictions take precedence" attached to `context` (with `--full`, the body is attached too), and it is also mentioned in one line in new contracts, so there is no need to append a pointer to the brief or hand-edit payloads (the payload of a task already emitted as `ready` stays unchanged, so write the addendum before emitting). Do not proceed past a block finding's stage until its remediation is confirmed. Rules for person and creative research are in `references/person-profile-research.md`.
3. Perform PARENT ACTIONS (parent-only blocks) directly. Only the parent accesses login and membership sources. If there are no sources that require access (access-broker, etc.), the fact that there is nothing to do is itself the action, and you must still mark completion with `done --run R --block <block>` so that `status` moves from active to complete and the downstream blocks unlock (if you do not mark it, `next` keeps surfacing the same block as PARENT ACTIONS).
4. When a child finishes, run `load --task T --file staging/out/T.jsonl` for each task. **Only `VERIFIED` counts as done** (a child saying "done" is not evidence). On `FAILED`/`PROOF FAILED`, classify the cause (missing contract → fix the brief, tool error → fix the environment, model limitation → escalate with `retry --option`), then `retry`.
5. Resolve `[BLOCKED]`, or `waive --reason` it (the reason is automatically recorded in limitations).
Done when: `next` prints `ALL DONE`. To confirm which models actually ran, follow the manifest procedure of the `subagent-orchestration` skill.

**P5 Analysis and refutation verdicts.** During the loop, diagnose with `gate` and `sql --recipe coverage|origin_share|agreement|saturation|claims|contradictions`. `stands` and `inconclusive` challenges do not create contradiction rows from newly loaded data onward (`stands` is a verdict that the refutation failed). The evidence ids referenced are preserved in the `[rlab challenge-context v1]` line of the challenge note, and `inconclusive` is shown in limitations. This rule applies only to newly loaded challenges; past contradiction rows in existing run ledgers were not migrated or deleted (a past `resolve --note` overwrote the source attribution, so owned challenges cannot be identified mechanically). For contradictions from past runs, compare the source text and the challenge records to distinguish them from substantive contradictions, and record the handling history and limitations. Handle many at once with `resolve --file`. Handle unresolved contradictions with `resolve --status resolved|disclosed`, and on a coverage/saturation soft gate failure the engine automatically reopens scout up to max_waves. For ad-hoc SQL analysis, use `sql` (read-only) or open `lake/parquet/*.parquet` directly with polars or duckdb (`references/data-lab.md`).

**P6 Deliverable.** In `reports/deliverable.md`, attach `[K0001]` to every factual sentence, leave anything unconfirmed marked "unverified", and include unresolved contradictions and a `## Limitations` section (`report` auto-generates a draft of the limitations). Done when: the `citation` and `contradictions` gates pass. Because `citation` is only a structural check (cited ids exist, Limitations section present), review `uncited_lines` and the semantic correspondence between sentences and claims yourself and record the result in limitations (for stakes=high, qa-review does an independent review).

**P7 Retro.** `retro --score <user rating 0-5, omit if none> --lesson "..."`. Without a score, only a proxy metric is recorded, and this reflects process health, not quality (`references/retro-learning.md`). Done when: the run, lessons, and mutation proposals are recorded in `registry.sqlite` and appear in the next `forge`.

## Pitfalls

- A child must put the receipt printed by `begin` into its meta. A guessed or reused receipt, or a truncated file (n_rows mismatch), is `PROOF FAILED`. This is the mechanism that filters out children who fabricated results without executing anything.
- Do not accept results via chat. The only output is the single JSONL file specified by the contract.
- After normalization (NFKC, whitespace, curly quotes), a quotation must be a **contiguous substring** of the source text. Quotes with ellipses, translations, or summaries are rejected. If a quote the model translated is rejected, strengthen the contract so that it quotes in the source's original language. If the source is raw HTML (such as a page fetched directly with `curl` in the collection or refutation stages), a sentence that looks continuous on screen is rejected if tags sit in between, because it is not a contiguous substring (`quote not found verbatim`). This rejection cascades to the challenges/claims rows that reference the quote, rejecting them as `unknown evidence id`. Prevent it by adding to the contract "do not join a sentence broken by HTML tags into a single quote; quote only continuous text fully contained inside a tag," and for rejections that have already occurred, drop only the affected rows (and the rows referencing them) with `load --accept-rejects`, commit the rest, and record the case in limitations (cheaper than rework, and other valid verdicts are unaffected).
- A row's `kind` is a parser selector only when it is a canonical row kind (candidates|sources|evidence|claims|challenges|findings). For findings-only blocks, write the classification value (e.g., `missing_lane`) in `kind`; for blocks mixed with claims and evidence, write `{"kind":"findings","type":"<classification>"}`.
- An intentional zero-row output (no candidates, no data matching the question) passes only if the meta has `"n_rows":0,"empty":true,"blocker":"<reason>"`. A plain empty file is treated as a failure.
- In an environment where `delegate_task` is unavailable, the parent can perform the contracts directly, in order. This is not an independent model review (especially for double coding and refutation), so record this fact in limitations.
- At `init`, the brief, questions, and workflow are copied as **snapshots** into `tasks/<T>/input/` for each task. If the brief, sources, candidates, or questions changed before dispatch, regenerate the inputs and contract of the not-yet-emitted planned tasks, with the same code used at creation, by running `rlab refresh-inputs --block B` on that block (run `--dry-run` first) (task ids change). If even one task has been emitted, started, or retried, it is rejected to prevent duplicate work; in that case, revert with `unready`/`retry` or create a new wave with `reopen`. Tasks that were already dispatched see the old inputs. When changing sensitive conditions such as permissions or prohibitions, use `grep -rn` to find the old values across the whole run directory and make sure no copies remain.
- Do not edit the `workflow.json` of a running run. Structural changes (adding or deleting blocks) mean `forge --fork` → a new run, and operating-rule reinforcement is done with `addendum.md` + the dispatch context (see P4).
- `raw/` is immutable (overwriting it breaks citation verification and hashes). Source text is stored locally for research, and only short quotations go into deliverables.
- Do not collect or store private personal information (real names, addresses, family, schools, workplaces). Sources the collector flags with `pii:true` are automatically excluded from extraction, and the parent handles them with `source drop`/`set --pii clear`. However, because collect stores the original text first, after-the-fact blocking alone is not enough: state the prohibited categories in the collection contract in advance and have the collector **delete the entire line** before saving (the remaining lines stay verbatim, so citation verification is preserved), and before extraction the parent re-checks `raw/` with grep.
- The sandbox deliberately masks the host `.env`. If an external API key is needed, do not try to read it; ask the user to pass the variable name through `docker_forward_env` (the user sets this on the host), and for cookies have the user place an exported youtube.com entries file in the run-specific secrets path. Either way, never accept values in chat, and only the parent uses them. For transcription cost and limits, see `references/external-stt.md`. The exact commands to set on the host are two steps: ① `hermes config set <VAR_NAME> "<value>"` (the value is automatically split off into `.env` and does not remain in config.yaml) ② `hermes config set terminal.docker_forward_env '["<VAR_NAME>", ...existing entries...]'` (this overwrites the existing array, so first check the current value with `hermes config get terminal.docker_forward_env` and merge). After forwarding, on the session side check only `env | grep <VAR_NAME>` and the length (do not echo the value itself), and if possible verify the actual integration with one harmless call.
- If the `access` trait is gated and the brief restricts credentials to parent-only use, it is not enough to run access-broker once: **every acquire step that needs those credentials (especially collect) must be handled exclusively by the parent.** Have scout (web exploration) find only candidate identifiers (handles, URLs) without credentials, and have the parent perform the actual authenticated lookups (API calls) as a PARENT ACTION and register them with `rlab source add`, and only then let the extract-stage subagents read that registered material. If you miss this, the Collector subagent either fails trying to collect with credentials it does not have, or a prohibited credential hand-off becomes necessary.
- If some questions apply **not per entity but to the whole platform/environment** (e.g., "does this platform's own ToS conflict with reuse?"), do not have a subagent investigate it repeatedly for every entity; have the parent investigate it **once** as a PARENT ACTION, reach a fixed verdict, record the result in the addendum, and apply it in common to that question for all entities (but state per-entity exception conditions, e.g., the verdict differs for a private account, in the addendum as branching rules). Investigating a platform-level question as many times as there are entities wastes budget and risks producing different answers.
- Present plans and lists you ask the user to approve directly in the response, as **file links (MEDIA) and paths** (do not make them ask where the document is). If the only thing to approve is a theory design document, first build a concrete list and a per-cell verification table and show them together (see "concrete list for approval" (`승인용 구체 목록 만들기`) in `references/personality-frameworks.md`).
- A model majority vote is not fact-checking. Reliability (κ) is only a coding-consistency metric, and claim status is decided by the number of independent sources.
- `waive` is not a way to save cost but a record of risk acceptance. Write the reason specifically and carry it into the deliverable's limitations.
- Do not let tooling eat the analysis. Allocate time to P5 and P6 (verdicts and writing), and do not spend it on infrastructure tuning.
- Run commands that may take several minutes or more (transcription, downloads, speaker diarization, retries) with `background=true` from the start. Run in the foreground, they hit the tool limit and die with SIGKILL (137), and the output is cut off so you cannot tell success from failure. For this reason scripts must always be resumable (skipping already saved results), and after a kill, judge status by the **number of saved files**, not the log.
- When reporting progress or speed, first check that the process is alive and that the mtime of the last saved file is close to the current time (log lines remain even after a deadlock), and report only measured values, in this order: done/total (ratio), average speed over the last N minutes (audio-minutes per minute, playback multiple, items per minute), number of failures, cost of this stage and cumulative cost (against the cap), and estimated remaining time. If you lost time to a defect in your own code, report the cause, impact, and remedy as they are, without hiding anything.
- When the user asks for "ideas for overcoming the limitations," do not just list ideas; first test each option's effect with the current data (relaxing a rule means running a variant; for alternative sources, aggregate their scale), then present a per-limitation table (option, effect, cost, user burden) with a recommended order, and say that limitations that cannot be overcome are subjects for Limitations. First determine whether the bottleneck is the rules or the supply of material (`references/person-profile-research.md` item 13).
- If you turn on completion notifications for every shard, retry, and auxiliary test of background jobs, each notification creates a response turn. Attach notifications only to the aggregation jobs that end a stage, and answer notifications for jobs you have already incorporated with just a sentence or two such as "incorporated, no change."

- **The specialist-domain review loop is already operated through documents and separate skills.** Non-expert approvers tend to approve a presented proposal as is, so before asking for approval, have it go through review → revision → re-review by high-capability subagents from different model families. The codebook-stage procedure is already contained in `references/codebook-iteration-lessons.md` and the `codebook-revision-validation-loop` skill, and the user has confirmed it works. Do not reimplement it as engine blocks (expertise trait, adjudicate/panel, subagent synthesize) (this was implemented once and rolled back on the user's instruction, and it duplicates the existing loop). Whether it is needed for stages beyond the codebook (analysis, synthesis) should be extended only after confirming with the user. Separately, as feedback: when a low-cost parent model (Sonnet-class or Terra-class) took sole charge of question design, contradiction resolution, strength judgments, and writing, quality dropped. Keep the parent on orchestration and verification, and leave judgment work to high-capability subagents.
- **Put collection restrictions (no storage, text and metadata only, etc.) in the brief only when there is a user instruction or a legal basis.** If the agent by its own discretion sets a reduction of material types in the name of "privacy protection" as the default, questions that can only be decided with images or audio (humor, purity, etc.) end up being decided from a one-text-sample-per-entity, which costs re-branching and rework. For each restriction, write its source (user|legal|agent), rationale, and the questions it weakens in brief §5, do not impose an agent restriction without a rationale, and confirm with the user in one line. Decide in the qtree, for each question, the material types required for a verdict and the minimum sample per entity, and if a restriction nullifies this, flag it in the `workflow-critic` stage. Divide restrictions into three layers. ⓐ For material-type reduction, "keep minimal exposure," no inheriting permissions, or default bans on external transmission/ZDR of membership material, the underlying activities are **allowed by default**; impose such discretionary restrictions only when instructed by the user or supported by a legal basis. ⓑ Protection of real people (private personal information, author-identifying information) and ⓒ access and credentials (cookies, passwords, designated accounts, login material only for the parent) are maintained by default, but **the user can choose to lift them per run**. When they choose, write the user's instruction and its scope in the brief, and do not interpret that choice as automatically lifting legal or platform constraints or essential credential protection. If the scope of application is ambiguous, confirm. Do not assume that collecting and retaining for research is always permitted under copyright; examine the actual manner of use separately from the applicable law and terms. Publication and redistribution of the source text are judged separately. If the original must not be stored, view it transiently and store only descriptive text (keep derivatives only), and the analysis proceeds as is.
- Running 4 concurrently on the same model (e.g., M-Terra-Balanced) can produce `HTTP 429 new-account-rpm` (20 calls per minute per model). The engine limits the concurrency of the same option to `max_per_option` (default 3) and holds excess tasks as `[WAITING FOR SLOT]` (`capped` in `next`), and `retry` automatically classifies the failure reason and leaves a tag such as `[env:rate_limit]` (can be specified explicitly with `--cause env|contract|model`). Because this is an environment error, not a contract or model limitation, do `retry --task T --option <model from a different family>` and then re-dispatch; sending to a model with looser limits (M-Haiku-Balanced) is also an option. Leftovers of the prior attempt (`staging/incoming/<T>/`, `T.attemptN.jsonl`) remain, so have the child rewrite the output with a new `begin` receipt.
- `HTTP 402` (billing/credits exhausted) is a different category from `429` (per-minute call limit): 429 is temporary congestion that clears with waiting or spreading calls, but 402 means that provider/model account's credits have actually run out, so it recurs even if you switch to another model behind the same provider and does not clear with waiting. If 2 or more tasks delegated in the same block and wave all have 402 as their last failure on the same option, the engine automatically halts at `retry` time (a `halt` event; `next` reports the halt). A `ready` task whose child could not `begin` because 402 occurred at delegation time is also recorded as a delegated attempt when you `retry` it and counts toward the determination. Once halted, stop re-dispatching and ask the user to choose between "top up credits vs switch to another provider/model." If they decide to wait for a top-up, leave the run as is (the workflow, brief, and questions are preserved), report only the fact of the halt, and when a decision is made, resume with `rlab resume --reason "..."` and only then run `next --dispatch` again. If, after switching model/provider and retrying, a **different** model returns 402 again within a few seconds to a dozen seconds, it is not a particular model but a **billing problem for the whole account (OpenRouter, etc.)** — do not switch to yet another provider a second time; stop right away and ask the user about billing status. Conversely, `HTTP 401` (`invalidated oauth token`, especially with ChatGPT/Codex subscription logins) is not about credits but means **that provider's login session was cut off**, and it does not clear with waiting or retrying — run only that task with another provider/model, tell the user only that re-login (`hermes auth add <provider> --type oauth`) may be needed, and keep going (do not block the whole session). If the user tells you they have switched to a subscription account (e.g., ChatGPT Plus/Pro) rather than a paid API, then any later 402 is merely "quota exhausted → wait for reset," so do not report it each time until the reset and quietly space out retries. When the same subscription account returns `HTTP 429` (`usage limit reached ... resets in Xh`, i.e., a form with a reset time embedded rather than rpm-congestion wording), it is the same in nature as 402, an **account-level quota exhaustion** — but since it commonly takes 1–2 hours to reset, instead of waiting for the reset, immediately revert the task to planned with `retry --task T` and re-dispatch to a **model from a different provider family** (if the ChatGPT/Codex family is blocked, another option such as Anthropic or DeepSeek), which clears it instantly with no waiting. Switching the same task only to another model of the same subscription provider gets blocked in the same way, so you must change the provider family itself.
- If the dataset lane has no tabular data, `data-analyze` automatically expands to 0 items (normal). Numeric comparisons based on official terms are handled by extract→compare-matrix.
- The moment `next --dispatch` prints the payload, it marks the task `ready` (emitted, delegation unconfirmed) and does not change it to `dispatched`. Subsequent `next` calls do not emit it again but show it as `[EMITTED, NOT CONFIRMED]`, and it occupies a slot. If you delegated, confirm with `rlab dispatched --payload F` (or the child's `begin`); if you postponed without delegating, revert it to planned with `rlab unready --payload F` (attempt count and receipt unchanged). Use `retry` only for attempts that were delegated and failed. The payload is a short, fixed ASCII pointer; if you need the full text of the contract, use `next --full`, and `next` without `--dispatch` writes only `dispatch_dryrun.json`.
- **In any tool call**, when putting Korean or other non-ASCII text into a string parameter, do not hand-type `\uXXXX` Unicode escapes (this recurs not only in `delegate_task`'s `context`/`goal` but in every parameter that takes a JSON string, such as `content` and `old_text` of `memory`/`context_notes`). If there is a typo, the whole batch is rejected with `Invalid \uXXXX escape` as in `delegate_task`, but even **without** a typo, if a hand-computed code point is wrong it passes without rejection and is silently delivered as different characters (mojibake) such as `입력`→`입륥` (for tools with no rejection at all, such as `memory patch`, `old_text` does not match the stored original byte for byte and keeps failing with "No entry matched"), and not being rejected does not guarantee it was correct. Write the plain UTF-8 string directly into the parameter (the tool handles JSON encoding). If `memory patch` fails with "No entry matched," do not retry immediately; copy the actual stored original returned in the error's `closest_entries` exactly and use it as `old_text`. Do not shorten or edit a payload issued by `next --dispatch` by hand; pass it as is (see the payload item above).
- Do not guess the provider from a `delegate_task` option name (name similarity has nothing to do with the provider). Among the F family, only `F-Sol-*` and `F-Sonnet-*`, and among the M family, only `M-Terra-*` and `M-Haiku-Quick`, connect directly to openai-codex/anthropic; all the rest, including `M-Haiku-Balanced` (F-DeepSeek/GLM/Qwen, M-DeepSeekPro, M-Qwen-Lite, L-GLM-Extract, Free-Nemotron, MM-*), go through OpenRouter (`M-Haiku-Balanced` also calls `anthropic/claude-haiku-5.5` via OpenRouter — assuming "Haiku = direct Anthropic" is wrong). If you need to avoid only particular providers because OpenRouter credits are exhausted, grep the `delegation.backends.model_map.options[].provider` field in `/hermes-home/config.yaml` directly to confirm the actual provider, and do not infer it from the name. Rather than cross-checking by hand each time, use a ready-to-run one-liner: `grep -A2 "name: " /hermes-home/config.yaml | grep -B2 "provider: openai-codex\|provider: anthropic" | grep "name:"` extracts only the non-OpenRouter option names, so put them in `--available` (conversely, if you must exclude OpenRouter entirely rather than avoid only some providers, this result is directly the safe list).
- If the scout lane returns only generic topic-related documents (news, case law, general-purpose FAQs) regardless of the **specific candidate entity list** (brand or site names, etc.) given in the questions and brief, the coverage gate fails repeatedly and scout keeps being reopened. Add directly to the context of scout tasks in wave 2 and later: "list the target entities not found in the previous wave and find each entity's **own** primary documents (official policies, API guides, etc.)" — the lane's generic guidance alone does not let the model narrow the scope.
- The audit finding `origin_merge` (block) means documents from the same publisher were split into separate origin_groups, inflating the count of independent sources. Before extraction, the parent should merge them with `rlab source --id S --origin <merged group> set`. If you removed the adversary from a lightweight workflow, a `challenge` gate fail is a subject for waive + limitations. This pitfall applies not only to "documents split by the same publisher" but equally to **derivative documents the parent created itself** (e.g., a memo that transcribes a verdict inherited from another run, or a common-verdict memo summarizing several sources) — when registering an original and the parent memo that summarizes or inherits it, register them in the same origin_group from the start, before source-audit flags it. You can fix it after registration, but getting it right from the start saves a turn.
- In a fork where you `--drop` scout and the parent seeds candidates/sources directly with `rlab source add` (vision analysis, re-evaluation rework, etc.), **the `input/sources.jsonl` (or `candidates.jsonl`) of tasks already created by `next --dispatch` may be frozen as a pre-seed snapshot (often 0 rows)** — this is the cause of source-audit and extract-single children returning an empty result saying "the input is empty." `retry`/`unready` only revert state and do not regenerate the snapshot, so right after seeding, **before emitting**, rebuild the inputs with `rlab refresh-inputs --block B` (run `--dry-run` first) (no manual overwriting needed). Tasks that have already been emitted are rejected, so revert them to planned with `unready` first and then run it. Together with the procedure for integrating vision analysis (image evidence) into the text pipeline, see the "vision evidence integration" section of `references/blocks-and-forge.md`.
- If the collected source text is garbled into U+FFFD (e.g., m.hanacard.co.kr is EUC-KR), the parent should recover it with `curl` followed by `decode('euc-kr')`, save it to `staging/incoming/parent/`, register it as a new source with `rlab source --file --url --title --tier --stance --origin --as-of add`, and then run extraction wave 2 with `reopen --block extract-single`. If you leave the garbled source alone, one representative candidate drops out of the comparison.
`reopen` does not touch tasks that have already been emitted, so `tasks/T/input/evidence.jsonl` of existing analysis tasks is not updated. For planned tasks not yet emitted, rebuild the inputs against the current ledger with `rlab refresh-inputs --block B`; for tasks already emitted, use the same command after `unready`, or take the input from a new-wave task.
- When the parent writes `deliverable.md` directly in P6, do not classify the entity×Q comparison table by simply checking whether a claim text contains keywords (`"tier1"`, `"exclude"`, etc.). The `compare-matrix` block produces cross-comparison claims that mention several entities in one sentence (e.g., "A's and B's high risk... the tier1 exclusion is maintained"), and other entity names or the string "tier1" are mixed into them, which confuses the target entity. Base each entity's final verdict only on the dedicated claim (mostly `block='compare-matrix'`) that **begins with that entity's name**, as in `SELECT id, text FROM claims WHERE question_id='Q7' AND text LIKE '<entity>%'`, and cite cross-comparison claims only as "remarks."
- If you run tens to hundreds of one-shot CLI calls such as `resolve`/`source set` in a shell for-loop, Python startup overhead (~1–2 seconds per call) accumulates and hits the 180-second foreground timeout. Even on timeout the loop itself does not die and items already processed have changed state, so call the same command again, check the remaining count with `gate`, and rerun as much as is missing (splitting into several calls is safer than raising timeout_s excessively to finish everything at once).
- When the first `_meta` line of a child-submitted JSONL interpolates a shell variable like `$RECEIPT` together with Korean text (e.g., a blocker reason) inside a bash heredoc (`cat > f << EOF ... EOF`), the content looks normal when viewed with `cat`, yet `check` sometimes emits `PROOF FAILED: missing _meta line` (cause: the shell's multilingual locale and quote handling can silently alter bytes; confirmed because the same template passes with ASCII-only content). When the parent writes JSONL output directly (zero-row handling, collect on behalf of a child, etc.), if even one line contains Korean, write the whole file with the `write_file` tool instead of a heredoc to avoid this problem — use heredocs only for ASCII-only content.
- If the adversary or source-audit raises a doubt about an API fact the parent has already collected (e.g., an account's current post count), saying "web search snippets show a different value," the snippet's timing is unclear, so do not trust the snippet and flip the number right away; **have the parent call the same API again directly to re-verify**. If the API reconfirms the originally collected value, correct the conclusion from "lookup failure" to "the content actually disappeared/was reset in the meantime," and record this conclusion in `reports/` to close the subagent's doubt with evidence.
- Skill file edits are possible only through `skill_manage` fuzzy patches, so arguments can be silently erased. Right after an edit, verify with compilation and `selftest.py`, and when reverting, reverse-patch based on the before/after sha256 in `/hermes-home/skills/.curator_ledger.jsonl` and the originals at `/hermes-home/.curator_backups/blobs/<sha>`, then compare per-file hashes. When comparing against the original with self-improvement (curator edits from other sessions), use the same ledger and blobs, but exclude your own session's edits via `evidence.session_id` and aggregate line-level diffs per file (first see whether the engine and catalog changed or only documents changed). Before reporting that something "was not incorporated" into a skill, search all other skills and references with `grep -rn` (the same capability may exist in a separate skill).
- When the user instructs you to "refer to" an operating-policy decision applied to one run (e.g., a decision to accept a known legal/ethical risk) in the question verdicts of related runs, separate that decision in addendum.md into **its own section (§0, etc.)** and state explicitly that "this decision is only a risk-acceptance choice and does not change the rights or legality verdict itself." Whether the collection means are permitted (does the platform allow our means?) and the rights-chain verdict (does the original author's right persist?) are different axes, so applying a single policy-decision context to all questions indiscriminately contaminates the verdicts of different questions. Pin down in one sentence each which questions it affects and which it does not, and include that in the dispatch context.
- When reporting or summarizing to the user the status of a run that continues from earlier session(s), do not rely only on chat logs found with `session_search`. A chat log is just an intermediate state at that point; in later sessions the actual completion state may have changed per `rlab status`/`gate`, or the final conclusions (excluded/on hold/confirmed complete, etc.) may already be recorded in `reports/deliverable.md` or project-local note files (`docs/*-local-notes.md`, etc.). Before reporting, always cross-check by reading the current block and gate status with `$RLAB status`/`gate` and reading deliverable.md and the local note files directly with `cat`, and only then summarize (do not assert status from chat alone).
- robots.txt is merely a crawler-convention notice, and the larger the platform, the more commonly its Terms of Service (ToS) body contains a separate clause (e.g., Content Licensing/AI-Scraping Terms) that explicitly prohibits "data scraping" regardless of robots.txt. In Q2 (whether the collection means are permitted) or accessibility verdicts, do not stop after checking only the official API documentation and skip the ToS of the access path you will actually use (direct web-page viewing, RSS, or other routes that bypass the API) — a "no problem" verdict holds only if you check both the robots.txt and the ToS body of the very path through which the data is actually fetched.
- "Access secured," "rights chain confirmed," and "the content actually fits the research purpose" are separate, independent axes. Do not finalize a candidate just because access and rights verdicts are done; have a person read measured samples (actual excerpts of the scraped source text) and check purpose fit separately (e.g., "humor-post sourcing" where it is actually a general-purpose popular-post aggregation of politics, current affairs, etc.). If you assume a candidate fits the purpose merely from the channel/site name or its blurb ("collection of best posts," etc.), then even with access and rights all clean, you waste time by researching every candidate and filtering out the unusable ones only at the end.
- If you removed a block with `forge --fork ... --drop <block>` but that block is still referenced as a reopen target in **another block's `on_fail` mapping** (`on_fail: {"coverage": "scout", ...}` in `assets/blocks.json`), the dead reference remains in the saved run's `workflow.json`, and on a soft gate failure `status`/`next` **crashes** with `TypeError: 'NoneType' object is not subscriptable` at `bstate(run, tgt)["waves"]` (the dropped block's name does not appear in the error trace, so the cause is hard to identify). Remedy: either beforehand, or right after the crash, use `grep -n '"on_fail"' <run>/workflow.json` to find the on_fail that points at the dropped block and patch it to `"on_fail": {}` for that block (this is a bug fix, not a structural change, so it is an exception to the "no editing a running workflow.json" principle). It blows up especially in re-evaluation forks that often drop scout (vision-analysis re-judgment, etc.).
- When an extract-single child receives a **single source document mixing multiple entities (accounts, etc.)** (e.g., one file of observation notes on 15 accounts), it sometimes submits a single evidence row with `entity=null` and packs per-account verdicts into the `note` field separated by semicolons (check passes). If this goes forward as is, the next stage (analyze-claims) cannot unpack the packed note and produces only 1–2 claims. For a newly dispatched wave, state in the context "if per-account verdicts are packed in the note field, parse them and make a separate claim/evidence row per account" and it is solved immediately. The problem is a **task already committed as `VERIFIED`** — `begin --task` rejects it with exactly `"ERROR: T#### is already verified"`, so rework is fundamentally impossible. In that case the parent parses the evidence `note` directly and fills in the missing accounts' claims by directly INSERTing into the `claims` + `claim_evidence` tables via SQL (mirroring the column composition of existing claim rows), but you must state in the addendum and the deliverable's Limitations that this is the **parent's restatement, not independent subagent coding**. This manual INSERT will blow up later unless you do two things together: ① IDs are issued by `run.nid("K")` (= the `ctr:K` counter in the `meta` table, not `max(claims.id)`), so right after the manual INSERT, if you do not advance the counter with `UPDATE meta SET v=<highest inserted number> WHERE k='ctr:K'`, the **next normally dispatched analyze-claims/compare-matrix child** gets IDs from the old counter value and fails `check` with `UNIQUE constraint failed: claims.id` (the cause surfaces much later in a child's output and is hard to trace — if you did a manual INSERT, fix the counter immediately). ② `claims.strength` allows only the enum (`weak|moderate|strong`); if you put a `ctype` value (`interpretation`, etc.) there, the insert itself succeeds but afterward `rlab status`/`next` **crashes the entire engine** with a `KeyError` at `STRENGTH_ORDER[c["strength"]]` in `expand_block`. Before a manual INSERT, check the allowed values with `SELECT DISTINCT strength FROM claims` and use only values within that set.
- Even if `compare-matrix` (and other `single` fanout analysis blocks) passes with `CHECK OK`, it may not cover every entity of the input entity_matrix — for example, of 15 candidates only 11 get a dedicated claim of the form "@handle: Q7=tier...", and the rest are mentioned only in passing in cross-comparison claims that bundle several entities ("if activity alone takes priority, A and B stand out, but..."), so their verdicts are effectively missing. This is because `check` verifies only row counts, citations, and proof, not "does every entity in the input also appear in the output." Immediately after `load`, exhaustively cross-check with `SELECT id, text FROM claims WHERE question_id='<Q>' AND block='compare-matrix'` whether each entity name appears at the start of a dedicated claim (names mixed inside cross-comparison claims do not count — see the "entity×Q comparison table" item above), and for missing entities, if the task is already `VERIFIED`, supplement them with the same parent direct INSERT procedure (the nid counter advance + strength enum check procedure right below) citing the same evidence ids as the existing claims, then reflect this in the deliverable. "CHECK OK" is only a format check and no guarantee of entity coverage completeness.
- When multiple sites reuse the **same standard ToS template** (a phrase common in Korean communities such as "...영리목적으로 이용하거나 제3자에게 이용하게 하여서는 안됨", roughly "must not be used for commercial purposes or made available to third parties"), the grammatical ambiguity of a clause (whether "영리목적으로" ["for commercial purposes"] also modifies the later "제3자에게 이용하게 하는 것" ["making it available to third parties"]) applies equally to all the sites that use that template. If one of the sites using the template spells out the same prohibition in more explicit wording in a separate notice or FAQ (e.g., "영리 또는 비영리 목적으로... 제3자에게 제공하지 않습니다", "we do not provide it to third parties for commercial or non-commercial purposes"), that explicit wording can also be used **as grounds for resolving the ambiguity for the other sites using the same template** — far cheaper than seeking separate legal advice per site, and it cross-checks the usual interpretation of the standard clause (a ban on third-party use regardless of commercial or non-commercial purpose).
